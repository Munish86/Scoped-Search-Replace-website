You ran a quick SQL query to swap an old URL for a new one. The posts look fine, but a page builder layout is suddenly empty, a slider has lost its slides, or a plugin is back on its default settings. Nothing was deleted: the data is still there, PHP just can no longer read it. The reason is serialized data.

What serialized data is

WordPress, themes and plugins often need to save a group of settings, a list or a whole layout in one database field. PHP turns such a structure into text with serialize() and back with unserialize(). The text looks like this:

a:2:{s:4:"logo";s:31:"http://old.example.com/logo.png";s:4:"link";s:22:"http://old.example.com";}

Read it as: an array (a) with 2 items; a string (s) of 4 characters, logo; a string of 31 characters, the logo address; and so on. Every piece of text carries its exact length.

Why a plain replace breaks it

Replace http://old.example.com (22 characters) with https://www.example.com (23 characters) using SQL's REPLACE(), or a text editor on a database export, and you get:

a:2:{s:4:"logo";s:31:"https://www.example.com/logo.png";s:4:"link";s:22:"https://www.example.com";}

The texts are now 32 and 23 characters long, but the value still says 31 and 22. unserialize() fails, WordPress gets false instead of the settings, and the theme or plugin falls back to its defaults. If the setting is saved again in that state, the old values are gone for good.

Only replacements that keep the length the same are safe by accident, which is rarely the case for URLs: http to https alone adds one character.

Where you find it

  • Post meta: page builder and theme settings per page, sliders, custom field plugins storing groups or repeaters.
  • Options: widgets, theme settings, most plugin settings.
  • Rarely in post content, which is mostly plain HTML and block markup.

Some builders use JSON instead of serialization. JSON has no lengths, so a replace doesn't break it the same way, but it often writes slashes as \/, so a search for a full URL may find nothing. Search for the domain alone in that case.

How to replace inside it safely

The safe way is the reverse of how the data was made: unserialize the value, replace the text in every string inside it, at every level, and serialize it again. PHP then writes the new, correct lengths.

That is what Scoped Search & Replace does for every value it changes. It also handles two edge cases that are easy to miss:

  • Values that are already broken (for example by an earlier plain replace) can't be unserialized. They are skipped, left exactly as they were and listed by ID, instead of being damaged further.
  • A serialized plain string (a single text, serialized) is serialized again after the change, so the plugin that stored it still reads it the way it expects.

If the damage is already done

  1. Restore the backup you took before the replace. This is by far the simplest fix.
  2. No backup? The values can sometimes be repaired by recalculating each s:n by hand or with a developer's script. It is fiddly: count bytes, not characters, for non-English text.
  3. Otherwise, open the affected pages or settings and set them up again.

Next time: back up, search and count first, and use a tool that understands serialization.
